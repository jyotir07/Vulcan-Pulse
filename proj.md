# Vulcan Counterfactual Engine

> **A payment ecosystem simulation and counterfactual reasoning engine inspired by Razorpay's Vulcan foundation-model approach.**

## 1. Project Overview

### One-line pitch

**Vulcan Counterfactual Engine lets payment teams ask "What if?" questions about their payment ecosystem and estimates the downstream impact before they make a change.**

Examples:

* What if an issuer's UPI success rate drops by 15%?
* What if payment traffic increases by 30% during a festival?
* What if Gateway A goes down for 20 minutes?
* What if 20% more customers switch from cards to UPI?
* What if we reroute 25% of traffic from Gateway A to Gateway B?
* Which merchants and customer segments are most exposed to an issuer outage?

The project is inspired by the central idea behind Razorpay's **Vulcan**: learning a reusable representation of payment behavior from large-scale, structured payment data and using that representation across multiple payment intelligence tasks.

This project does **not** attempt to reproduce Razorpay's proprietary Vulcan model or use real Razorpay data.

Instead, it builds a smaller, fully reproducible research/product prototype using synthetic payment data.

# 2. Why This Project Exists

Payment systems are highly interconnected.

A single transaction depends on many variables:

```text
Customer
   │
   ├── device
   ├── location
   ├── historical behavior
   │
   ▼
Merchant
   │
   ├── category
   ├── size
   ├── traffic
   │
   ▼
Payment Method
   │
   ├── UPI
   ├── Card
   ├── Netbanking
   │
   ▼
Issuer / Bank
   │
   ▼
Gateway / Route
   │
   ▼
Payment outcome
```

A change to one part of this network can propagate through the rest of the system.

Traditional dashboards describe what happened.

Traditional prediction models estimate what is likely to happen.

The goal of this project is to explore a third capability:

> **What is likely to happen if the system changes?**

That is the counterfactual problem.

# 4. Project Goals

## Primary goals

1. Build a realistic synthetic Indian payment ecosystem.
2. Learn representations of payment transactions using a transformer/set-based architecture.
3. Build a baseline predictive payment model.
4. Build a counterfactual simulation layer.
5. Estimate the effect of changes to the payment ecosystem.
6. Visualize the predicted impact.
7. Provide explainable reasoning behind predictions.
8. Demonstrate the system through an interactive dashboard.
9. Benchmark counterfactual predictions against known synthetic ground truth.

## Secondary goals

* Demonstrate cold-start behavior.
* Demonstrate robustness to distribution shifts.
* Compare learned models against rule-based baselines.
* Show uncertainty around predictions.
* Make every experiment reproducible.

---

# 5. Non-Goals

This project should **not**:

* Claim to reproduce Razorpay's Vulcan.
* Use private Razorpay data.
* Scrape or reverse-engineer Razorpay systems.
* Present synthetic results as real-world payment statistics.
* Build a production payment gateway.
* Process real customer financial information.
* Pretend that synthetic simulation results represent actual Indian payment infrastructure.

The README should explicitly describe this as:

> **A Vulcan-inspired research and engineering prototype built on synthetic payment data.**

# 8. Synthetic Data Must Contain Relationships

Do not generate completely random data.

The dataset needs meaningful correlations.

For example:

```text
UPI
+
certain issuer
+
peak hours
+
high traffic
        ↓
higher timeout probability
```

Another:

```text
new customer
+
new device
+
large transaction
+
unusual merchant
        ↓
higher risk
```

Another:

```text
Gateway A
+
merchant category = travel
+
peak traffic
        ↓
higher latency
```

These relationships allow the model to learn something meaningful.

# 9. Payment Failure Taxonomy

Synthetic failures should have realistic categories.

Example:

```text
INSUFFICIENT_FUNDS
ISSUER_DECLINED
UPI_TIMEOUT
GATEWAY_TIMEOUT
NETWORK_ERROR
AUTHENTICATION_FAILED
FRAUD_REJECTION
LIMIT_EXCEEDED
UNKNOWN
```

Failure probabilities should depend on context.

For example:

```python
base_failure_rate = 0.03

if peak_hour:
    failure_rate += 0.01

if issuer_degraded:
    failure_rate += 0.05

if gateway_degraded:
    failure_rate += 0.07
```

The actual implementation should use a probabilistic simulator rather than a large collection of brittle if-statements.

# 10. Payment Representation Model

The model should represent a payment as a **set of fields** rather than treating it like natural language.

Example:

```text
amount = 2400
payment_method = UPI
issuer = HDFC
merchant_category = travel
city = Bangalore
hour = 21
device = Android
gateway = gateway_a
```

Each field receives an embedding.

Conceptually:

```text
Field Name        Value
────────────────────────────
amount            ₹2,400
method            UPI
issuer            HDFC
merchant          travel
city              Bangalore
hour              21
device            Android
gateway           A
```

These embeddings are passed into a Set Transformer or equivalent attention-based encoder.

Output:

```text
Payment
    ↓
[128-dimensional representation]
```

The exact embedding size should remain configurable.

---

# 11. Pretraining

The initial model should use self-supervised learning.

## Masked Field Prediction

Randomly mask one or more fields.

Example:

```text
amount = ₹2,400
method = UPI
issuer = [MASK]
merchant_category = travel
city = Bangalore
hour = 21
```

The model predicts:

```text
issuer = HDFC
```

Repeat across the dataset.

This forces the model to learn relationships between payment attributes.

# 15. Counterfactual Calculation

At a high level:

```text
Baseline transactions
        │
        ▼
Baseline prediction
        │
        ▼
Baseline metrics
```

Then:

```text
Apply intervention
        │
        ▼
Generate modified transaction context
        │
        ▼
Run modified context through model
        │
        ▼
Counterfactual metrics
```

Finally:

```text
Counterfactual
      -
Baseline
      =
Estimated Impact
```

# 18. Recommended Actions

The system can optionally generate mitigation strategies.

For example:

```text
Scenario:
Gateway A unavailable
```

Possible interventions:

```text
Gateway B +10%
Gateway C +15%
UPI traffic reroute +20%
```

Evaluate each intervention.

```text
                 Success Rate

Current          94.7%

No action        88.2%

Strategy A       91.4%

Strategy B       93.1%

Strategy C       94.0%
```

The engine can then show:

> Strategy C produces the highest simulated recovery under the current model.

Important:

The project should clearly label this as **simulation output**, not a guaranteed real-world result.

# 19. Ground Truth

This is one of the most important parts of the project.

Because the data is synthetic, the simulator knows the true generating process.

For example:

```text
True intervention:

HDFC success rate:
95% → 80%
```

The system can compare:

```text
True impact
vs
Model-predicted impact
```

Metrics should include:

* MAE
* RMSE
* calibration
* confidence intervals
* relative error

This prevents the project from becoming a visually impressive but scientifically unvalidated demo.

# 22. Cold-Start Experiment

Hold out some merchants during training.

The model should never see those merchants.

Then test:

```text
Known merchant
vs
Unknown merchant
```

Likewise:

```text
Known issuer
vs
Unknown issuer
```

This tests whether the representation actually learns reusable ecosystem relationships instead of memorizing entity IDs.

---

# 23. Distribution Shift Experiment

Train on:

```text
Normal traffic
```

Test on:

```text
Peak/festival traffic
```

Measure performance degradation.

This is particularly important because payment systems experience highly non-stationary traffic.

# 26. Explainability

Every counterfactual should have a short explanation.

Example:

> **Why is this scenario causing a 3.8 percentage-point drop?**
>
> HDFC represents 21% of UPI transactions in the simulated ecosystem. The affected traffic is concentrated among high-volume merchants during peak hours, where gateway capacity is already near saturation.

The explanation should be generated from actual simulation/model outputs.

Avoid generic LLM explanations that invent causes.

# 27. Optional LLM Layer

An LLM can be used as the natural-language interface.

User:

> "What happens if HDFC's UPI reliability drops by 15% for half an hour?"

LLM:

```text
Structured scenario
{
  issuer: HDFC,
  method: UPI,
  success_delta: -0.15,
  duration: 30m
}
```

The LLM should **not perform the numerical prediction**.

It only translates natural language into a structured scenario.

The actual simulation should be deterministic and model-driven.

This distinction is important.

# 36. Important Limitations

The project must explicitly state:

1. The data is synthetic.
2. Results do not represent real Razorpay payment performance.
3. The simulator has known assumptions.
4. Counterfactual estimates are only as good as the underlying data-generating process and model.
5. Real-world payment systems contain factors that may not be represented in the simulation.
6. The project is inspired by publicly described concepts around Vulcan and is not an implementation of Razorpay's proprietary system.

# 38. Final Guiding Principle

Do not optimize this project for the number of features.

Optimize it for one compelling loop:

```text
             ASK
              │
              ▼
       "What if X?"
              │
              ▼
          SIMULATE
              │
              ▼
          PREDICT
              │
              ▼
          EXPLAIN
              │
              ▼
          MITIGATE
              │
              ▼
        SIMULATE AGAIN
```

If this loop is accurate, reproducible, visually compelling, and backed by quantitative experiments, the project will be substantially more impressive than simply building another payment chatbot or another transaction classifier.
